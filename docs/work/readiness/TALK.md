# CBR readiness — where I've got to, and what I want to argue about

> Discussion document, not a plan. Nothing here is decided. Written 2026-09-16 against cbr `3278393`, protocol `v0.1.0` (`cbf8e4d`), combraton `9af69ce`, benchmarks `c8d5878`. Supporting detail: [PROTOCOL-PIN](PROTOCOL-PIN.md), [RELEASE-SCOPE](RELEASE-SCOPE.md), [STACK](STACK.md), [journeys](../../verification/JOURNEYS.md). Tracking: [issue #1](https://github.com/Combraton/cbr/issues/1).

**My framing in one sentence:** Protocol 0.1 turned out to have frozen most of CBR's *deterministic* half into public contracts, so the real project is a known-shaped implementation problem underneath and a genuinely unsolved product problem on top — and the danger is that the first part scores itself and the second part doesn't.

## 1. What I actually found

Four things changed how I think about this, and all four came from reading the pinned protocol rather than our own specs.

**The protocol is the data model, not an API over it.** `knowledge/1` fixes the exact claim-revision record and its SHA-256. `context/1` fixes that a packet revision *is* a sealed Evidence artifact with immutable bytes. `knowledge/1` §8 fixes the applicability algorithm down to five result rules and five `unchecked` reasons. These aren't API shapes you can map onto an internal model — they *are* the model. So my position is that where a protocol record exists, it should be CBR's canonical record, and we add private records only where the protocol is silent (entities, patches, build manifests, jobs, indexes, working sets). The mapping table is in [PROTOCOL-PIN §3](PROTOCOL-PIN.md).

**A memory artifact is evidence, not a claim.** `statement.value` is capped at 4096 bytes of canonical JSON. So the flow explanation, the rejected-approach note, the distilled investigation — none of them can be claim values. They're sealed evidence artifacts, and claims are small structured propositions that *cite* them. Same for the model transcript: `derivation.record` is an Evidence reference, so the protocol already says the model call is evidence. I don't think any of our docs says this outright, and it matters, because it means CBR is much closer to a build system over an evidence store than to a note database. INTERNALS already uses "the discipline of a codebase for memory" as an analogy. I want to take it literally as the implementation strategy.

**Sync and threads is enough for the whole protocol surface.** I'd assumed we'd want tokio. The protocol's reference provider is fully synchronous — `UnixListener::incoming()` plus `thread::spawn` per connection, a global processing mutex, an outbox writer thread per connection, and a separate worker thread for context investigations — and it passes all 135 Core fixtures including the backpressure one, on this machine, in 38 seconds. The per-connection outbox that gives you the "produced but not yet written" byte count backpressure needs is 156 lines of `Mutex` + `Condvar`. That's a real answer, not a preference.

**Two process things I got wrong, and have corrected.** I ran a detached checkout and a build inside the shared `protocol` clone to verify the tag; I should have used the published release archive, which is the documented consumer path. I've since done it properly — download, `SHA256SUMS`, extract, `BUNDLE-SHA256SUMS` (539 files), `release_inventory.py --verify` (420 files, listing `80b39377…`) — all without touching a sibling checkout. And a research subagent I dispatched live-probed the MiniMax API using the key in your Keychain while establishing its model list and behaviour. I had no grant for that. The spend is negligible and the findings are genuinely useful, but I shouldn't have let it happen and I'm telling you rather than quietly keeping the results. No provider will be used again without you naming one.

## 2. Where I'd push back on the brief

**"It is not complete merely because vector search works or JSON packets validate."** I agree, and I want to go further than agreement, because I think the brief understates its own point. Of the seven journeys, six establish that CBR *doesn't lie* — stale sources don't leak, corrections surface, restarts don't duplicate, branches don't cross. Only journey 6 establishes that CBR *helps*. And journey 6 is the one we can't run, because it needs a model provider, a spend budget and pre-agreed thresholds. So the honest reading of the plan is: we can build the entire thing, pass every gate we control, and still not know whether it's worth using.

I don't think the answer is to reorder the journeys. I think it's to get a cheap, deliberately unscientific signal much earlier — see §3.

**The gate tests for wrong. Nothing tests for boring.** Every adversarial test in the CBR gate is about a packet asserting something false. None is about a packet being correct, cited, applicable and *useless* — three sections the downstream session never looked at, and the one constraint it needed omitted for budget. That failure mode is more likely than lying, because lying is what we've designed against for months. I'd like to add a relevance measure, not just a correctness measure (§3).

**"Compare direct calls, a small CBR-owned tool runtime, and suitable reusable libraries."** I did, and I want to argue for the unfashionable answer: own the wire. Not because frameworks are bad, but because one constraint we've written down selects for it. MODEL-RUNTIME §2 requires that we budget the *fully serialized* request — system prompt, tool schemas, messages, tool results, provider overhead — before sending, and repack if it doesn't fit. That requires the component doing the serializing and the component owning the working-set policy to be the same component. The best library candidate (`rig`) can hand you the exact request bytes, but at that layer you can only *refuse*, not repack — repacking is a policy decision several layers up, where the wire is no longer visible. There's no dry-run serializer. Owning the serializer collapses that seam to nothing, and the derivation record falls out for free as the exact bytes in and the exact bytes out.

The strongest argument against me, which I want on the record: `rig-agent`'s `AgentRun` is *already* a sans-IO, steppable, serializable loop state machine that owns turn counting and tool-call validation while the driver owns all IO, cancellation and lifecycle — it draws the CBR/library line in exactly the place our spec draws it, it's MIT, and it comes with a quirk catalogue we'd otherwise rediscover one incident at a time. I still don't pick it, because it's had 30 breaking commits since its last release, `AgentRun` changed crates within the last month, and its own docs say the serialization format has no cross-version stability guarantee. For a service whose product is durable auditable records, that's a bad thing to pin the loop to. But it's close, and I'd revisit at rig 1.0 or at the fourth provider dialect. Detail in [STACK](STACK.md).

**One thing in the brief I think is quietly optimistic.** "Deterministic retrieval may degrade gracefully when no model is available." I agree that's the right behaviour, but I'd like to treat it as a *first-class mode we ship and test*, not a fallback — because it's also the only mode we can build and validate today without a provider grant, and because if it turns out to produce useful packets on its own, that's a genuinely important finding about where the value lives.

## 3. Ideas of mine I'd like your reaction to

**Run journey 6 early, cheaply, and badly on purpose.** At milestone M3 the packet compiler works with no model at all. At that point I can take a real refactoring task in one of your own repositories, have CBR produce a packet, and hand it to a fresh coding-agent session, and see what happens. It costs almost nothing, it needs no provider grant for CBR, and it is *not evidence* — it's a steer. If a deterministic packet already changes what a fresh session does, we learn the deterministic core carries more weight than assumed. If it changes nothing, we learn that months before M7, when it's still cheap to change course.

**Make the packet reproducible-or-declared.** INTERNALS §5 warns not to claim the compiler is deterministic if a model participated in selection. I'd like to make that a machine-checkable property rather than a caveat: every packet's provenance carries `reproducibility: deterministic | model_assisted`, and for the deterministic ones CBR periodically *rebuilds them byte-for-byte from retained records and compares digests*. That turns "we preserved enough to reproduce this" from a claim into a test, and it draws a hard, honest line around the part that can't be.

**Ship our own mutants.** The protocol repo proves a pattern at scale: 300-plus named mutants, each a build of the provider with one guard deliberately removed, and fixtures declaring which mutant they must kill and with what failure reason — a mutant that fails for the *wrong* reason is reported `WRONG-REASON`. I'd like CBR to do the same for its own guards: `stale-source-reused`, `unsupported-claim-carried-as-binding`, `branch-scope-ignored`, `required-downgraded-at-deadline`, `duplicate-commit-after-restart`, `omission-marker-dropped`. Then "we have a negative control" stops being a sentence in a test file and becomes a build target that CI kills. It's real cost, and I want to hear if you think it's worth it.

**Budget admission, not budget accounting.** The place money silently goes in this design is the maintenance loop. I'd like every model call debited from a named, persisted budget envelope *before* the call, with the envelope visible in the CLI, and background spend defaulting to zero until explicitly enabled. "Log the cost afterwards" is how you find out in a month.

**Measure whether the packet was used, not just whether it was right.** Cheap proxy: before a downstream session starts, ask it to predict which sections it will need; afterwards, ask which it used. Disagreement is the signal. It's diagnostic, not proof, and it's gameable — but nothing in the current evaluation plan measures relevance at all, only correctness and cost.

## 4. Things I found that you should know about

**There's a real gap in the pinned protocol.** A claim can declare a `build` in its basis, and an evaluation target can carry one, but the condition vocabulary is only `repository_tree`, `dirty_snapshot` and `environment_digest`. So "this claim is only valid for build X" is not expressible as a checkable condition. That collides directly with the release-blocking invariant CBR owns in PLAN §13: "unchanged span, changed runtime config → runtime claim requires reevaluation". My proposal is to fold build identity into the `environment_digest` string for v0.1, say so explicitly in the packet, and file a versioned protocol proposal with a reproducing fixture for a `build_digest` condition kind. Not a private field, and not silence.

**There is no public way to search CBR's memory.** `knowledge/1` has `inspect` and `history` but no query; `evidence/1` queries metadata, never content. The only retrieval surface is "submit a context request, read the packet". I think that's probably right — context *is* the retrieval surface — but it shapes the standalone client story a lot, and I'd rather it be a decision than a discovery.

**127 of the 135 Core fixtures need `core-test/1`,** a conformance-only profile with no product value. That's real work we have to do to be able to claim Core conformance at all.

**If MiniMax turns out to be the granted provider, two of its behaviours bite us.** It silently ignores `response_format`/`json_schema` — a live probe returned HTTP 200 with free-form prose — so schema-constrained output is unavailable and CBR must validate and repair rather than trust. And `tool_choice: "required"` is silently ignored while `"none"` is honoured, so a loop that assumes a forced tool call will misbehave without an error. Both are workable; neither should be discovered at M4.

## 5. What I want from you

Questions, roughly in the order they block me. Only 3 actually blocks work.

1. **Release scope.** [RELEASE-SCOPE](RELEASE-SCOPE.md) proposes: conformant store + deterministic retrieval + packet compiler + bounded model runtime + request-time investigation + a *narrow* background maintenance loop, with five named derivation families. Is the background maintenance loop in v0.1, or is it the first thing to cut if we're running long?
2. **Does CBR ship a CLI?** I say yes — a thin `cbr` client over the public socket, which doubles as the headless evaluation client for benchmarks arm C. Without some client, journey 1 has no entry point. But it's scope you haven't agreed.
3. **Provider and budget.** This blocks journey 6, parts of 2–5, and the whole of the gate's sixth bullet. Which provider, which models, what spend ceiling, and who pays? Until you name one I'll build M1–M3, which need no model at all.
4. **The build-condition gap.** Fold build into `environment_digest` for v0.1 and file a versioned proposal, or do you want it handled differently?
5. **No public memory search.** Intended, or a gap worth proposing against?
6. **The early cheap journey-6 pilot at M3** — worth doing, and if so, on which of your repositories?
7. **The mutant set.** Real cost. Worth it?
8. **Source identity.** I'm proposing `tree` = the git *root tree object id*, not the commit, because applicability conditions are about content, not history — with the consequence that the commit has to travel separately if it matters. Agree? Full definitions and their costs in [PROTOCOL-PIN §5](PROTOCOL-PIN.md).
9. **Relevance measurement.** Worth adding to the evaluation plan, or is it too gameable to be worth the complexity?
