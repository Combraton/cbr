- **Status:** accepted and complete. The project licence, the model provider, the spend ceiling and the journey-6 pilot repository were all decided on 2026-09-16. Question 11, how source identity reaches git, was recorded on 2026-09-17 after M2's review; its named trigger fired at M3b on 2026-09-19 and that row records the move to `gix` and the acceptance it met. Question 12, how the Keychain is read, was recorded on 2026-09-20 at the m4b review, with its rejected alternative and the condition that would reopen it. Nothing in this record is unresolved.
- **Date:** 2026-09-16.
- **Authority:** the owner, answering the nine questions in [TALK §5](../work/readiness/TALK.md), after independent review of [PR #2](https://github.com/Combraton/cbr/pull/2) at head `b8ba7f3` against base `3278393`. - **Scope:** CBR-local implementation choices. Wire and compatibility decisions belong to Protocol; cross-system authority belongs to Combraton. This record selects nothing outside this repository.

## Problem

The readiness milestone produced proposals for release scope, stack, milestones and journey acceptance, and returned nine decisions requiring owner judgment. Without them, implementation could not start without either guessing or silently narrowing the agreed product.

## Affected contracts

Nothing on the wire. CBR remains pinned to Protocol `v0.1.0` (`cbf8e4df9df2ca8a9b50264df6acace6e4c3a0fc`), serving `core/1`, `knowledge/1`, `context/1` with `context.claims`, and `evidence/1` for its own packet and support bytes, plus `core-test/1` behind the conformance launch configuration. It calls `execution/1` and `verification/1` as a client only.

## Selected choices

| # | Question | Decision |
|---|---|---|
| 1 | Is background maintenance in v0.1? | **In, and narrow.** Coalesced triggers; background spend defaults to **zero** until explicitly enabled; foreground context requests take priority. It is not the first thing to cut. |
| 2 | Does CBR ship a CLI? | **Yes**, the `cbr` CLI as proposed in [RELEASE-SCOPE §2](../work/readiness/RELEASE-SCOPE.md), speaking the public protocol over the socket and doubling as the headless evaluation client. No privileged internal shortcut. |
| 3 | Provider and spend budget | **MiniMax**, on the owner's subscription quota, addressed through both dialects at one provider: OpenAI-compatible `https://api.minimax.io/v1` as the primary wire and Anthropic-compatible `https://api.minimax.io/anthropic` as the second. Models `MiniMax-M2.7-highspeed` (extraction, large-result projection), `MiniMax-M2.7` (ordinary derivation), `MiniMax-M3` (synthesis, request-time investigation, image input). Admission counts through `POST /v1/responses/input_tokens`. The mechanism is unchanged and now load-bearing: the persisted envelope is debited **before** every call, never reconciled after, and exhaustion is a typed `budget_exhausted` result rather than a retry loop — the quota is shared with the owner's own tools, so an overspend degrades them, not just CBR. Background spend stays zero until explicitly enabled. Full terms and consequences in [STACK §8.1](../work/readiness/STACK.md). |
| 4 | The build-condition gap (G1) | Define CBR's declared **environment fact set to include build facts**, so build identity is covered by `environment_digest`, and **say so in the packet** rather than leaving it implicit. Separately, file a `build_digest` condition-kind proposal on the Protocol repository **with a reproducing fixture**. No private field, no locally widened schema. |
| 5 | No public memory search | **Intended for v0.1.** Context is the retrieval surface. A local `cbr search` diagnostic is permitted provided it is **labelled non-protocol** and is never presented as a protocol operation or used by the evaluation client as a scored path. |
| 6 | The early journey-6 pilot at M3 | **Yes**, against **Knowscroll-v2** ([`Legend101Zz/Knowscroll-v2`](https://github.com/Legend101Zz/Knowscroll-v2), public), with its decision records `D-001`–`D-022` as the decision input and one open backlog task as the refactor. Labelled **pilot**: it is a steer, not evidence, and may not be cited as downstream-task evidence for the gate. Evidence capture redacts credentials **at the recording boundary**, not afterwards — that repository has already once seen a provider response carry a live third-party credential, so this is a known failure mode there rather than a precaution.  **Amended by the owner, 2026-09-20, at the m3c review: m3d has two pilot repositories, and this one is now the first of them.** Knowscroll-v2 stays the **decision-memory** pilot exactly as recorded above — ingest `D-001`–`D-022`, accept them as the owner decides, and show that accepted decisions appear as binding and superseded ones never appear as current. The second is the owner's **brian2 fork** (`Legend101Zz/brian2`), added as a **brownfield** pilot: 7,065 commits, 553 tracked files across Python, Cython, C++ and templates, and a working tree that is dirty by design. It is registered **read-only** at launch, by the same `--register-repository` flag, so its path never crosses the wire; CBR reads it and changes nothing in it. It holds no decision records, so its journey tests **discovery and code flow rather than decision memory**: the task is locating where units are dropped by `np.concatenate`, the request names no answer path, and **the owner writes the oracle before the run** — the facts a correct packet must contain and at least one trap — which this session neither writes nor sees beforehand. Because its tree is dirty, the packet's basis must carry the dirty snapshot, citations to modified files must resolve to the dirty bytes rather than to `HEAD`'s blob, and no packet may claim applicability to the clean tree; that is the first journey to exercise the dirty path, so it gets its own negative control — the same request at the clean tree must not be answered from the dirty bytes. Its Cython, template and other unanchored files are declared as coverage gaps by count and kind, and a packet that silently covers only the Python files is a failed run. **brian2 is CeCILL-licensed and this repository is MIT: none of its bytes, excerpts or packets are committed here** — digests, paths, spans, counts and costs only. Cost is recorded separately for each pilot: bytes indexed, index build time, time to first packet, store size after the run. |
| 7 | CBR's own mutant set | **Yes.** One mutant per named negative control in [JOURNEYS](../verification/JOURNEYS.md), built in **M6**, with `WRONG-REASON` reported when a mutant fails at the wrong step or for the wrong reason — the pattern the Protocol repository already runs at scale. |
| 8 | Source identity | **As proposed** in [PROTOCOL-PIN §5](../work/readiness/PROTOCOL-PIN.md): `tree` is the git root tree object id, not the commit. **Additionally, record the commit id in the evidence descriptor**, which removes the cost noted in that section — content identity governs applicability while the commit remains recoverable from evidence. |
| 10 | Project licence | **MIT**, the same text and holder line as Protocol. `LICENSE` at the repository root, `license = "MIT"` in `[workspace.package]`, inherited by every crate. | 11 | How source identity reaches git (recorded 2026-09-17, at the M2 review) | **The installed `git` binary, through plumbing commands with fixed arguments and no shell** (`rev-parse`, `status --porcelain=v2 -z`), in `crates/cbr-identity`. **This diverges from [STACK §6](../work/readiness/STACK.md)**, which proposed `gix`. **Reason:** M2 needs three reads: a commit's root tree id, the working-tree status, and nothing else. Git's own plumbing output for those is stable and specified, and taking `gix` for them would add a large dependency graph before any bulk tree or blob access exists to justify it. **Cost:** a runtime dependency on an installed `git`, which is refused with a typed error when absent, and no identity yet for a directory that is not a git checkout (PROTOCOL-PIN §5's non-git tree). **Trigger to move to `gix`:** the first of: M3's retrieval reading tree or blob contents in bulk (code anchors over a tree, not one `rev-parse`); a supported deployment without `git` installed; the non-git directory identity being scheduled; or process-spawn cost showing up in a measured request path. When one fires, `cbr-identity` moves to `gix` behind the same functions, and its property tests with their negative controls are the acceptance. **Fired, and the move is made (2026-09-19, M3b).** The first named trigger is the one that fired: M3's retrieval reads a tree's blobs in bulk to take code anchors, which is not one `rev-parse`. `cbr-identity` is now `gix` in process behind the same functions — `basis`, `git_basis`, `dirty_snapshot` — and gained `tree_entries` and `read_blob` for the bulk reads that caused the move. **The acceptance this row named held:** the four identity property tests with their negative controls pass unchanged, with two added for what `gix` newly reaches (a staged change, and a tree's blobs read back exactly). **The cost recorded above is gone:** there is no runtime dependency on an installed `git`, so the typed error for its absence no longer has an occasion. **What is unchanged:** a directory that is not a git checkout still has no identity (PROTOCOL-PIN §5), and a submodule is still a gitlink with no contents. |

| 12 | How the Keychain is read (recorded 2026-09-20, at the m4b review) | **The `security` tool at `/usr/bin/security`, with arguments fixed at compile time and no shell.** [READINESS §2](../work/m4/READINESS.md) stated the tradeoff before there was code: the tool adds no dependency but puts the secret through a child process's standard output, while a Keychain crate keeps it in-process and adds a dependency to the credential path. **The owner resolved the constraint that appeared to rule the tool out:** *"never passed to a child process"* means the secret is never **handed to** a child, by argument vector, environment or standard input. A secret read **back from** a child's standard output over a private pipe is not that, and the arguments name only the service. **Two reasons beyond the dependency count.** Keychain access control is **per program**, and `cbr-provider` is unsigned and rebuilt constantly, so an in-process read means either a prompt after every rebuild or an *Always Allow* granted to an unsigned binary — a worse position than trusting Apple's own tool. And it is how the owner's other tools already read this same key, so CBR is not introducing a second access pattern to the same secret. **Rejected alternative:** a Keychain crate (`security-framework` directly, or `keyring` above it). **What would reopen it:** a signed, notarised release binary, for which the per-program access control becomes an argument *for* the in-process read rather than against it. **The mechanism, each line of which has a test** ([`crates/cbr-provider/src/keychain.rs`](../../crates/cbr-provider/src/keychain.rs)): an absolute path, never a `PATH` lookup; `find-generic-password -w -s minimax_api_key` fixed at compile time with the service name a constant rather than configuration; the child's environment cleared, its standard input the null device, its standard output a pipe and its standard error discarded unread, because a failure message from that tool is not CBR's to vet; a timeout after which the child is killed and the launch refused with a typed reason; a non-zero exit, empty output, or output that is not a single line refused the same way; **no fallback to an environment variable, a file or any other source, on any platform**; the bytes zeroed on drop, never `Debug`-printed, never serialized, and going only into a request's `Authorization` header; read **once, at construction, and only when a model is configured**. On Linux and in CI a configured model is a **refused launch** with a typed reason. Every test of the mechanism runs against an injected fake tool, so **no test on any machine reads the owner's key**. |

Two design statements accepted alongside them, both now recorded in [PROTOCOL-PIN §3](../work/readiness/PROTOCOL-PIN.md):

- Derived artifacts are sealed under a CBR-specific derivation source kind with CBR as producer, never a captured-observation kind.
- A derived artifact cited as claim support declares ancestry roots naming the **captured evidence it was derived from**, never itself. Negative control: a claim supported only by two derived artifacts sharing one captured root must report `single_lineage`.

## Alternatives considered and rejected

Cutting the maintenance loop to a later release was available and refused: the CBR gate names maintenance as a substantive capability, and deferring it would have been a scope reduction requiring its own explicit decision. Adopting `rig-agent`'s loop was the strongest library alternative and is rejected for now on churn and serialization-stability grounds, revisitable at rig 1.0 — the full argument, including the case against this decision, is in [STACK §8](../work/readiness/STACK.md). Tokio was rejected on direct evidence from the protocol reference provider rather than preference ([STACK §2](../work/readiness/STACK.md)). Adding a public search operation was rejected as a protocol change CBR does not need in v0.1.

## Consequences

Milestones M1 through M3 proceed immediately and still need no model provider — that independence was designed in and is worth keeping even now that a provider exists, because it is what lets M3 answer *"is the deterministic packet useful on its own"* without a model in the room to flatter the answer.

With the grant in place, **M4 can be accepted on live evidence and M7 can start.** What remains blocked is narrower and has a different cause: journey 7 waits on a PIO release, and the ten executor-bearing `composition` fixtures wait on an execution peer. Neither is a spend question.

Two obligations follow from *how* the grant is framed. The quota is **shared with the owner's own tools**, so the budget envelope is no longer only a cost control — an overspend degrades the owner's working environment, which makes debit-before-call load-bearing rather than tidy. And a 5-hour window plus a monthly ceiling are **two counters with different reset semantics**: the month can be almost untouched while the window is exhausted, so the envelope carries both and admission checks both. A single monthly counter would let CBR pass admission and still starve the owner's next session.

The `cbr search` diagnostic and the mutant set are additions to the proposed scope, not reductions. The commit-id addition to the evidence descriptor is a small widening of CBR's own descriptor use, not a protocol change.
